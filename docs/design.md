# Architecture and Design Decisions

## Objective

Model a customer onboarding process that accepts requests, validates their contents, waits for a review decision, and records the outcome.

## Scope

This reference implementation uses fictional business customers and synthetic data. It demonstrates workflow orchestration and reusable infrastructure.

Identity verification, credit decisions, and regulatory compliance checks are outside its scope.

## Request Data

Each request contains:

- Business name
- Contact name
- Contact email
- Request ID generated by the application
- Creation and update timestamps
- Current status

## Request Lifecycle

| Status | Meaning |
|---|---|
| SUBMITTED | Request stored and awaiting validation |
| PENDING_REVIEW | Validation passed; awaiting a decision |
| APPROVED | Reviewer approved the request |
| REJECTED | Reviewer rejected the request |
| INVALID | Required information failed validation |
| FAILED | A technical error prevented completion |
| EXPIRED | The review deadline passed |

Approval, rejection, invalidation, failure, and expiration are terminal states.

## API Behavior

### POST /requests

Accepts business name, contact name, and contact email.

Returns a generated request ID and initial status after the request is stored and workflow execution starts.

Malformed input returns a client error. Failure to start the workflow is recorded as a technical failure.

### GET /requests/{requestId}

Returns the request's current status and timestamps.

An unknown request ID returns a not-found response.

### POST /requests/{requestId}/decision

Accepts an APPROVED or REJECTED decision.

Only requests awaiting review can receive a decision. Duplicate or conflicting decisions return a conflict response.

## Workflow

1. Store the submitted request.
2. Start the onboarding state machine.
3. Validate required business and contact information.
4. Mark invalid requests INVALID.
5. For valid requests, register a callback token and mark PENDING_REVIEW.
6. Wait for an authorized review decision.
7. Record APPROVED or REJECTED.
8. Record EXPIRED if the review deadline passes.
9. Record FAILED for unrecoverable processing errors.

## Design Decisions

### Separate API handling from orchestration

Lambda functions handle API requests. Step Functions coordinates the lifecycle and review timeout.

### Use a callback for review

The workflow waits for a decision rather than repeatedly polling the database.

Callback tokens remain internal and are never returned to API clients.

### Store request state in DynamoDB

Request records provide a consistent place to retrieve status without exposing workflow internals.

Conditional writes protect state transitions. The implementation must also handle retries and partial failures between database updates and workflow callbacks.

### Bound retries

Transient service failures receive limited retries. Invalid input and conflicting decisions are not retried automatically.

### Protect API access

Authentication and authorization are required before external exposure. Review endpoints must restrict decisions to authorized reviewers.

The initial infrastructure must not expose unauthenticated decision endpoints.

### Limit logged data

Logs should identify request IDs, workflow steps, and errors without recording callback tokens or full customer payloads.

## Planned Verification

- Valid submission reaches PENDING_REVIEW.
- Invalid submission reaches INVALID.
- Approval reaches APPROVED.
- Rejection reaches REJECTED.
- Duplicate decisions are rejected.
- Unknown request IDs return not found.
- Review timeout reaches EXPIRED.
- Service failures follow bounded retry and failure paths.
